この機能はまだありません。[短縮 URL](/short-url) を自組織の Cloudflare
で動かすための手順の下書きです。名前や手順は実装までに変わることがあります。

コマンドは `apps/short-url` で、`vp exec` を付けて実行します（`vp run` は環境変数を引き継がず、出力をキャッシュするため使いません）。

## 1. データベースを作る

```bash
vp exec wrangler d1 create short-url                      # 表示された database_id を wrangler.jsonc に書く
vp exec wrangler d1 migrations apply short-url --remote   # テーブルを作る（更新のたびにも実行する）
```

## 2. `wrangler.jsonc` を書き換える

| 項目              | 書くもの                                                                  |
| ----------------- | ------------------------------------------------------------------------- |
| `name`            | Worker の名前                                                             |
| `routes`          | 短縮 URL のドメイン（Cloudflare で管理しているゾーンのもの）              |
| `d1_databases`    | 1 で作ったデータベースの名前と `database_id`                              |
| `vars.ACCESS`     | **必須。** Cloudflare Access の設定をまとめたもの（下の例）。5 で確かめる |
| `vars.EDITOR_URL` | 移る先の Message Editor。書かなければ `https://editor.cre.run/`           |

```jsonc
"vars": {
  "ACCESS": {
    "allowedEmailDomains": ["example.com"],         // 短縮 URL を開けるメールアドレスのドメイン
    "teamDomain": "example.cloudflareaccess.com",   // Access のチームのドメイン（メールのドメインとは別）
    "aud": "<5 でコピーする AUD タグ>"
  }
}
```

秘密の値は、ここには書きません（`wrangler.jsonc` はリポジトリに入ります）。

## 3. `BOT_KEY` を登録する

Bot が短縮 URL を作るときに付けるキーを、Worker の Secret `BOT_KEY` に登録します。Bot にも渡すので、作った値を控えます。

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
vp exec wrangler secret put BOT_KEY   # 上の値を貼る
```

`BOT_KEY` がないあいだは、作ることも開くこともできません。

## 4. デプロイする

`CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` を環境変数（CI ならシークレット）に入れて、デプロイします。
API トークンは、テンプレート「Edit Cloudflare Workers」に D1 の編集を足し、対象を 1 つのアカウントに絞って作ります。

```bash
vp exec wrangler deploy
```

## 5. Cloudflare Access をかける

短縮 URL を開けるのを、組織のメールアドレスでログインした人だけにします。Access は `wrangler.jsonc` では設定できないので、ダッシュボードで行います。

1. Worker の「Access」タブで「Protect this Worker behind Access」を選び、ポリシーに「メールアドレスのドメインが一致する」（2 の `allowedEmailDomains` と同じ）を設定します
2. Bot が使う `/api/` だけを外します。Zero Trust の「Access」→「Applications」で `short.example.com/api/*` のアプリケーションを作り、ポリシーを **Bypass** にします
3. 1 の Access の設定画面で「Application Audience (AUD) Tag」をコピーし、`ACCESS.aud` に書いて、もう一度デプロイします

サーバーは、Access がリクエストに付ける JWT（`Cf-Access-Jwt-Assertion` ヘッダー）の署名を確かめ、その中のメールアドレスのドメインが `allowedEmailDomains` に入っているときだけ判定データを返します。Access をかけ忘れたり、ポリシーを誤って広げたりしても、組織の外の人には開けません。

## 6. Bot に `BOT_KEY` を渡す

3 で控えた `BOT_KEY` を、Bot のシークレットの管理機能か環境変数（例: `CRE_SHORT_URL_BOT_KEY`）に置きます。
Bot は、短縮 URL を作るときに `Authorization: Bearer <BOT_KEY>` を付けます（[短縮 URL を作る](/short-url#短縮-url-を作るbot-の開発者向け)）。
キーが漏れたら、3 と同じ手順で `BOT_KEY` を作り直し、Bot の側も置き換えます。

## 7. 確かめる

```bash
curl -i -X POST https://short.example.com/api/links
```

`401` が返れば、`/api/` が Access から外れていて、`BOT_KEY` も設定されています（`BOT_KEY` を付けていないので断られた）。
`503` なら `BOT_KEY` か `vars.ACCESS` が、`302`（Access のログインへの転送）なら 5 の `/api/` の除外が、正しく設定されていません。

最後に、`BOT_KEY` を付けて見本データの短縮 URL を 1 つ作り、組織のメールアドレスでは開け、外のメールアドレスでは開けないことを確かめます。

## ローカルで動かすとき

`apps/short-url/.dev.vars`（リポジトリに入れない）に、ローカル用に作った `BOT_KEY` と、Access の設定（`teamDomain` はテスト用の公開鍵を返すローカルのサーバー）を書きます。ローカルには Access がないので、テスト用の鍵で署名した JWT をヘッダーに付けて開きます（そのためのスクリプトは実装時に用意します）。

```dotenv
BOT_KEY=<ローカル用に作った値>
ACCESS={"allowedEmailDomains":["example.com"],"teamDomain":"localhost:8788","aud":"short-url-dev"}
```

```bash
vp exec wrangler d1 migrations apply short-url --local
vp exec wrangler dev
```
