# ガイドサイト駆動開発（Guide Site Driven Development）

ユーザーガイドを「あとから書く説明書」ではなく「先に合意する仕様であり、開発のゴール」として扱う。
ガイド・E2E・スクショ・動画を、AI が外れたときに引き戻す **ハーネス** として使う。

> このスキルは立ち上げ段階。ここには大枠の方針だけを置き、具体的な手順やツールは
> 人と AI の対話の中で決まったものから育てていく（末尾「このスキルの育て方」）。

## 解決したいこと

- ガイドが機能開発のあとに書かれ、いつも遅れる
- ガイドの手順・仕様が、実際の動きとズレる
- ガイドのスクショ・UI が、今の画面とズレる

## 基本の考え方

1. **使う人が見るものを、先に書く** — 作り手の言葉ではなく、使う人の言葉で手順を書く
2. **それを「できた」の基準にする** — 書いたとおりに動けば完成。迷ったらガイドに戻る
3. **確かめ続ける** — ガイドの手順を E2E にし、通ったときだけスクショ・動画をガイドに戻す
4. **人は絵で判断する** — AI はテキスト（コード・ログ）を、人はスクショ・動画・画像差分を見る
5. **数えられるものは機械で止める** — ルールは書くだけでなく、型・Lint・テスト・CI・フックで落とす

README 駆動開発・Working Backwards（PR/FAQ）・ATDD と同じ「先に書く」に、AI と自動テストを足したもの。

## 2 つのガイド

| 種類                                                            | 縛るもの                                 | 確かめ方             |
| --------------------------------------------------------------- | ---------------------------------------- | -------------------- |
| 外部ガイド（ユーザー向け）                                      | 何ができればいいか                       | E2E・スクショ・動画  |
| 内部ガイド（AI・開発者向け。CLAUDE.md / AGENTS.md・ADR を含む） | 何を使い、どう分け、何をしてはいけないか | 型・Lint・テスト・CI |

外部ガイドだけだと「動くけれど読めないコード」になりうる。設計の約束は内部ガイドに書く。

外部ガイドには「手順」（何ができるか）のほかに「約束」（何が起きないか。データを送らない・残さない、など）がある。
約束は 1 件ごとに 1 件以上のテスト（E2E か単体テスト）で確かめ、約束の表の「テスト」列にテストへリンクするバッジを置く。
バッジのテスト名と実際のテストは機械で突き合わせ、どちらかだけ変えたら落とす。確かめられない約束は、その理由をガイドに書く。

## 基本の流れ

1. **ガイドを書き、人と合意する** — 手順・前提・期待する画面を相談して決める
2. **ガイドの手順を E2E にする** — 見出し（手順）と E2E の Step を 1:1 で対応させる。テストしない手順は理由を残す
3. **赤から始める** — 実装前の E2E は落ちる。そのエラーを「何が足りないか」の指示として読む
4. **通るまで回す** — 実装 → E2E → 修正を緑になるまで繰り返す
5. **画像で確かめる** — スクショ・動画を撮り、AI 自身もそれを読んでおかしければ直す
6. **人が承認する** — PR のプレビュー（ガイド・スクショ・画像差分）を人が見て、マージ＝承認

実装が先に変わってもよい（双方向）。その場合は E2E を回して画像を撮り直し、ガイドの文章を差分に合わせて提案する。

## 未リリースの機能のガイド

リリース前の機能のページにはバッジを付け、読んだユーザーがリリース前だと分かるようにする
（未リリースの機能を使えると誤解させない）。段階は次の 3 つ。

| 段階      | 状態                                             | バッジ                                     |
| --------- | ------------------------------------------------ | ------------------------------------------ |
| `planned` | ガイドだけがある（まだ触れない）                 | `<Badge variant="warning">planned</Badge>` |
| `preview` | プロトタイプ・モックを触れるが、機能は未リリース | `<Badge variant="accent">preview</Badge>`  |
| なし      | リリース済み                                     | 外す                                       |

- バッジはページ先頭（タイトル付近）と、frontmatter の `sidebar.badge`（`Planned` / `Preview`）の両方に付ける
- `preview` にするのは、プロトタイプを公開し、そこで何ができて何ができないかを本文に書いたとき
- バッジを外すのは、E2E が通り、スクショ・動画がそろって、機能がリリースされたとき

## AI が守ること

- **合意済みのガイドは勝手に変えない。** 変更が必要なら理由を添えて人に提案し、承認を待つ
- E2E が落ちたら、まず **実装を疑う**。テストやガイドを書き換えて通す逃げ道を使わない
- スクショ・VRT の **基準画像を勝手に更新しない**。意図した差分かどうかは人が決める
- 意図しない差分（関係ない画面の変化）は、元に戻す方向で直す
- E2E が通らない状態で、ガイドのスクショ・動画を更新しない
- 未リリースの機能のガイドから `planned` / `preview` バッジを外さない（外すのはリリースのとき。段階を進めるのも人と合意してから）
- 「期待どおりの見た目」はテストに書けない。迷ったら作り込む前に人に確認する

## このリポジトリでの現状

- 外部ガイド: `apps/docs`（Blume）。内部ガイド: ルートの `AGENTS.md`（Claude Code・Codex 共通。`CLAUDE.md` は `@AGENTS.md` を読み込むだけ）
- PR プレビュー: `apps/docs` と `apps/message-editor` は PR ごとに Cloudflare Worker Previews でプレビューを作り、URL を PR にコメントする（`.github/workflows/preview-*.yml`）
- E2E・スクショ・VRT: Playwright。ガイドの画像は E2E が撮り、CI で比較する（`references/e2e-and-screenshots.md`）
- 約束のガイド: `apps/docs/docs/message-editor/data-handling.mdx`。「テスト」列のバッジのテスト名と実際のテストは
  `apps/message-editor/tests/guide-promises.test.ts` が突き合わせる
- 動画の撮影方法は **未決**
- 未決の部分に触れる作業では、案を出して人と決め、決まったことをこのスキルに書き足す

## このスキルの育て方

- 対話の中で方針・手順・ツールが決まったら、このファイルか関連スキルへの追記を **AI から提案** する
- このファイルは概念と原則に絞り、100 行程度に保つ。具体的な手順は次のどちらかに切り出す
  - 同じディレクトリの `references/*.md`（例: E2E とガイドの対応ルール、撮影手順）
  - 独立したスキル（例: ガイド執筆用、E2E・動画作成用、カバー率チェック用）
- 「基本の考え方」と「AI が守ること」の変更は、必ず人の承認を得てから行う
- 同じ指摘を 2 回以上受けたら、ルールとして書くか、機械で止める仕組み（CI・フック）を提案する
- 本ファイルの実体は `.claude/skills/`、Codex 用の `.agents/skills/` はそこへのシンボリックリンク。編集は実体側で行う
